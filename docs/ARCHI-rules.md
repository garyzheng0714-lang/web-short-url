# 架构文档维护规则

[ARCHI.md](ARCHI.md) 记录 **web-short-url** 的真实架构。**每完成一个任务**（新功能 / 重构 / 修 bug）后，判断 ARCHI.md 要不要回写。

核心原则：**文档必须与代码现状一致。** 声明"完成"前，如果文档和代码对不上，就是没完成。

---

## 什么时候必须更新

任何改动只要动了下面这些，就要回写：

- **项目结构**：新目录、文件移动、新模块
- **技术栈**：新依赖、版本升级、换库
- **API 路由**：新增 / 删除 / 改路径 / 改鉴权（→ 第 8 章路由清单表）
- **数据库 schema**：加表 / 加列 / 改主键 / 新迁移（→ 第 10 章）
- **飞书登录**：新链路 / 改 token 流程 / 改 state 校验（→ 第 11 章）
- **session 机制**：动 token 通道 / cookie / 续期（→ 第 12 章）
- **上游代理或缓存**：新代理接口 / 改缓存策略 / 改 TTL（→ 第 13 章）
- **前端结构**：新页面 / app.js 模块划分变了 / 设计系统 token 变了（→ 第 14–17 章）
- **配置**：新环境变量（→ 第 7 章，**同时要改 `.env.example` 和 README**）
- **部署**：改 CI / 改 PM2 / 换域名（→ 第 23 章）
- **数据流变了** → 更新第 18 章的 Mermaid 图
- **技术债有增减** → 更新第 24 章（消掉一条要删行，新欠一条要加行）

---

## 按改动类型怎么更新

### 大功能 / 重构

**通读并逐一核对**这些章节：
- 第 2 章 概览（高层架构图还准吗？）
- 第 4 章 项目结构（文件树、行数）
- 第 5 章 核心架构原则（新改动违背了哪条原则吗？如果违背了，是原则该改，还是代码该改？）
- 第 8 章 API 设计（路由清单表）
- 第 18 章 数据流图
- 第 24 章 已知技术债
- 第 25 章 结论（"只记三件事"还成立吗？）

### 小功能 / 增强

只更新**直接相关**的章节。比如：
- 加了个 API → 第 8 章的路由表 + 可能的第 18 章流程图
- 加了个环境变量 → 第 7 章配置表
- 前端加了个组件 → 第 14 章

### 修 Bug

**通常不用改** ARCHI.md——除非这个 bug 暴露了**架构层面的缺陷**。比如：
- 修了个 cookie 丢失的 bug → 说明第 12 章的兜底机制有洞 → **要写**
- 修了个错别字 → 不用写

判据：**下一个接手的人会不会因为不知道这件事而踩同样的坑？** 会 → 写进去。

### 依赖变更

更新第 3 章技术栈表 + 任何受影响的架构章节。

## 怎么写

- **精确、如实**——写代码真实的样子，不写你希望它是的样子
- **简洁**——够understand就行，不复制实现细节（那是代码的活）
- **数据流变了就改图**（第 18 章的 Mermaid）
- **引用真实文件路径和行号**（`server.js:654`），别写"在某个 handler 里"
- **诚实记债**——第 24 章不许粉饰。发现新问题就加一行，解决了就删一行
- **不确定就标出来**——写 "⚠️ 未验证" 好过写一个漂亮的假设

## 体积控制

ARCHI.md 超过 ~20,000 tokens 会拖累每次读它的成本。

⚠️ **别用 `awk` 数中文 token**——在 macOS 上会崩（`awk: multibyte conversion failure`），token 数算成 0。用这个：

```bash
python3 -c "
import re
t = open('docs/ARCHI.md', encoding='utf-8').read()
cjk = len(re.findall(r'[一-鿿　-〿＀-￯]', t))
est = int(cjk * 0.7 + (len(t) - cjk) / 4)
print(f'≈ {est} tokens（{len(t)} 字符，其中中文 {cjk}）')
"
```

**基线**：≈ 7157 tokens（上限的 36%）。

超了就手工瘦身（合并冗余、删过时内容），**别靠删有用信息来减肥**。
