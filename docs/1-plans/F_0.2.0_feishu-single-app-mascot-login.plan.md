# 飞书登录迁移：双 App 双按钮 → 单应用 + Mascot 登录页

**版本**：0.2.0（上一版 0.1.0）
**日期**：2026-07-14
**依据**：`~/.claude/skills/feishu-login-guide` v4（单应用统一登录）+ v6（Mascot 视觉基准）

---

## Overview

把现在的**双 App 双按钮**飞书登录（FBIF App + 富的 App，登录页两个按钮 + 扫码 Tab），迁移成 skill 规定的 **v4 单应用统一登录**：只保留 FBIF 一个 App（`cli_a917cf34dffa1cb0`），富的员工靠飞书后台的「**关联组织应用共享**」走同一个 App 登录。登录页同步换成 **v6 Mascot 版**（门+小黄人插画双栏卡片 + 单个「使用飞书登录」胶囊按钮）。

保留端内 SSO 免登（用户裁决），删掉扫码。

---

## Problem Statement

现状（v3 legacy）的代价：
- **2 组凭证**（FBIF + 富的各一套 App ID/Secret），两个 secret 混用就是 `99991663` 错误
- **2 个飞书后台**（改配置要富的管理员配合）
- **4 条 redirect URL 白名单**
- **登录页 2 个按钮 + 扫码 Tab**：用户要先判断"我是哪家公司的"才能点对按钮——这是把内部组织结构泄漏成用户负担
- 13 条后端路由（6×2 + logout）

skill v4 的判断：单应用后 1 组凭证、1 个后台、1 个按钮、富的后台零操作，运维减半。生产 feed.foodtalks.cn 已验证可行。

## 归一 vs 新增

本次是**纯归一**，没有任何新增入口。

| 方案 | 怎么做 | 新增几个概念 | 代价 |
|---|---|---|---|
| **归一（选它）** | 富的员工复用 FBIF 那一个 App / 一条 OAuth 链路 / 一个按钮，靠飞书后台的关联组织共享认出他们 | **0**（还减掉 3 个：富的 App、租户选择、扫码 Tab） | 需要用户去飞书后台开一次共享 |
| 新增（现状，否决） | 富的一个独立 App + 独立按钮 + 独立扫码 Tab | 3 | 双凭证、双后台、4 条白名单、用户要自己判断公司 |

**判据**：优雅 = 用最少的新概念达成目的。用户点登录时**不该需要知道自己属于哪个租户**——这是系统该自己搞清楚的事。归一后按钮从 2 个变 1 个，用户的选择负担直接消失。

**卡了一下的地方**：就在这。我得先想"我算 FBIF 的还是富的的？"——**这个问题根本不该由用户回答**。它是内部组织结构，泄漏成了用户的认知负担。点错了还会失败（点了富的按钮但你是 FBIF 员工 → 飞书报无权限）。右上角还有个扫码角标，又是一个"我该走哪条路"的岔口。

**Rams 十条自检**：
- **#4 自解释**：一个按钮，无需说明。旧版要用户自己判断公司归属，不自解释。
- **#6 诚实**：不再假装"这是两个系统"——它本来就是一个系统。
- **#10 less but better**：2 按钮 + 扫码 Tab + 切换链接（4 个决策点）→ 1 个按钮（0 个决策点）。

**交付前怎么验**：Playwright 登录真实页面 + fullPage 截图扫查（列宽/图标/呼吸感/断行/hover/错误态/移动端窄屏）。

## 登录链路影响（高危章节）

**这次改动直接动登录链路本身——这是本项目最容易摧毁的地方。**

### ⚠️ 风险 0（最重要）：对富的来说这是「能力替换」，不是「能力新增」

**旧路会被删掉**（富的专用 App 的 6 条路由 + 凭证），新路（关联组织共享）**必须先证明可用**。

如果「关联组织应用共享」在 FBIF 后台不可用 / 这个 App 没有共享入口（该功能仍在逐步开放，官方文档不保证每个 App 都有入口），那么这次迁移就是**把富的的登录能力砍掉却没给替代品**——这是净损失，不是优化。

**富的现在 0 用户，所以即时影响是 0；但能力损失是永久的。**

**因此：「共享开通 + 富的真人登录成功」是发布硬门槛，不是可选验证项。** 见下方「部署顺序」。

### 碰到 session 了吗？碰到，但**4 条 token 通道全部保留不动**
cookie / `X-Session-Token` header / `Authorization: Bearer` / `?session_token=` query —— `extractSessionTokens()` 和 `resolveSession()` **一行不改**。`public/app.js` 开头的 `window.fetch` 猴补丁也不动。

### 碰到飞书登录了吗？**这就是本次改动的主体**

| 链路 | 现状 | 改后 |
|---|---|---|
| OAuth 按钮 | fbif + fude 各一条 | **只留 fbif**（富的员工也走它） |
| 端内 SSO 免登 | fbif + fude 各一组 | **只留 fbif**（用户裁决：保留免登） |
| 扫码 | fbif + fude 各一组 + Tab 切换 | **删除**（v6 登录页无扫码） |

路由：**13 条 → 5 条**（login / callback / sso-config / sso-exchange / logout）。

### ⚠️ 风险 1：签名密钥会变（可接受）
`signingSecret()` 现在派生自 `sha256(fbif_secret + "|" + fude_secret + "|shorturl-state-v1")`。删掉富的 secret 后，派生输入变了 → **签名密钥变了 → 所有在途的 state 立即失效**。

- **影响**：部署那一刻正在飞书授权页上、还没点"确认"的人，回调时会看到"登录失败请重试"，重新点一次即可。
- **窗口**：state TTL 只有 10 分钟。
- **结论**：可接受。但要在验证时留意，别把它误判成 bug。

### ⚠️ 风险 2：富的员工的 open_id 会变（**当前无影响，但必须记录**）
飞书的 `open_id` 是 **App 维度**的——同一个人在不同 App 下 open_id 不同。富的员工原先通过富的 App 登录（open_id 属于富的 App），改走 FBIF App 后会拿到**全新的 open_id**，系统认不出他是老用户，**历史记录会全丢**。

**为什么这次不构成问题**（已实测生产库）：
```
生产库 users：郑梽煌 ×2（一条 tenant=fbif，一条是 v2→v3 迁移遗留的空 tenant）
生产库 富的租户用户数：0
生产库 link_history 总条数：0
```
**富的一个用户都没有，历史一条都没有** → 零迁移风险。

**但如果将来富的已有用户再做这种迁移**，必须先用 `email` 或 `union_id` 做身份映射，不能直接切。已记入 ARCHI 技术债。

### 碰到 `users` 表了吗？碰到，但**不改 schema**
- `users.open_id` 继续是 `fbif:ou_xxx` 格式（`localUserId()` 不动）——**动了会让现有 session 全部失效**。
- `users.tenant` 之后恒为 `"fbif"`（它现在只是路由标记，不再代表企业）。
- **真正区分两家企业靠 `users.tenant_key`**（飞书 user_info 返回的真实企业 ID）——这一列已存在，富的员工登录后 tenant_key 仍是富的自己的。

### 碰到 cookie 设置了吗？没碰
`finishLogin` / `handleSsoExchange` 里的 cookie + hash 双通道兜底逻辑**原样保留**。签名 state 的"cookie 缺失时放行"逻辑也**原样保留**（改回"必须有 cookie"= 飞书端内用户全挂）。

## Test Impact

本项目无自动化测试，门槛是**真实环境验证**。

**要 curl 的接口**：
```bash
curl -i /auth/feishu/fbif/login        # 期望 302 → accounts.feishu.cn?client_id=cli_a917cf34dffa1cb0
curl -i /auth/feishu/fbif/sso-config   # 期望 200 {"appID":"cli_a917..."}（只有 appID，绝不能有 secret）
curl -i /auth/feishu/fude/login        # 期望 404（fude 路由已删干净）
curl -i /auth/feishu/fbif/qr-config    # 期望 404（扫码已删干净）
curl -sf /api/health                   # 期望 200
curl -o /dev/null -w "%{http_code}" /api/config   # 未登录期望 401
curl -o /dev/null -w "%{http_code}" /             # 未登录期望 303 → /login
```

**真实浏览器要验的**：
1. `/login` 渲染 Mascot 版：≥lg 左插画右表单双栏、**1 个按钮**、无扫码/无教程/无问号/无游客链接
2. 窄屏（<1024px）单栏，插画隐藏，不塌
3. **Network 面板：两张图先于 JS 下载**（preload 生效）
4. 点按钮 → 跳飞书 → 授权 → 跳回 → 进主页 → **刷新仍在登录态**
5. 错误态：手工访问 `/login?error=denied` → 显示红色错误条
6. Console 无报错

**登录链路重验**：

| 链路 | 谁来验 | 什么时候 | 性质 |
|---|---|---|---|
| **富的账号 · 走现有 `/auth/feishu/fbif/login`** | ❌ 我验不了，**需要用户 + 富的同事** | 🔑 **改代码之前**（门槛①） | 🔴 **不过就一行代码都不动** |
| FBIF 账号 · 浏览器 OAuth 按钮 | ✅ **我能验**（我自己的账号） | 改完代码，本地 + 部署后 | 合并前必须过 |
| 富的账号 · 新 Mascot 单按钮 | ❌ 需要用户 | 部署后（门槛②） | 回归，不过就 revert |
| 端内 SSO 免登 | ❌ 我验不了（需真实飞书客户端） | 部署后 | ⚠️ 如实标"未验证"，请用户在飞书里打开一次 |

⚠️ **"富的登录"不是可选项，而且必须在动代码之前验。** 它是这次迁移的**核心能力**——现有路由 `/auth/feishu/fbif/login` 迁移后不变，所以共享一开通就能拿它验，**不用等拆完房子再看地基**。不许因为"富的反正 0 用户"就跳过。

## 部署顺序（硬门槛，不许跳步）

> **⚠️ 执行状态（2026-07-15 更新）：门槛① 被用户主动跳过。**
> 用户决定"先不测富的，FBIF 能登就行"，并选择"按原规划全删"。因此**代码已在未验证富的登录的前提下改完**。
> 这不是悄悄绕过——是记录在案的主动决策。代价：万一以后富的要用、而关联组织共享其实没生效，恢复要改代码 + 重新部署（不是加个按钮那么快）。当前富的 0 用户 0 历史，即时影响为 0。
> 富的验证（原门槛①的 0b/0c/0d + 门槛②）**顺延到"富的实际要用的时候"**再做，见第 24 章技术债回写。

### 🔑 门槛 ①：**改代码前**就验证富的能登进来（不过就一行代码都不动）

**关键洞察（Codex 提出）**：`/auth/feishu/fbif/login` 这条路由**现在就存在，迁移后也完全不变**。所以共享一开通，**用现在的线上代码就能验证富的员工能不能通过 FBIF App 登录**——完全不需要等破坏性部署之后。

**先验地基，再拆房子。**

**步骤：**

1. **用户**：https://admin.feishu.cn（FBIF 管理员）→ 关联组织 → 应用共享 → 把 App（`cli_a917cf34dffa1cb0`）共享给「富的文化传媒（上海）有限公司」
   - 参考：官方《关联组织功能实践》https://www.feishu.cn/hc/zh-CN/articles/762346821295
   - ⚠️ **找不到入口 / 这个 App 不支持共享 → 立即停止迁移，一行代码都不改**。该功能仍在逐步开放，官方不保证每个 App 都有入口。

2. **富的同事**：验证他能不能通过 **FBIF 应用**登录。

   🚨 **别让他在登录页上点按钮——他一定会点错。**

   现在线上是双按钮。富的同事看到「使用 FBIF 飞书登录」和「使用富的飞书登录」，本能会点**富的**那个 → 然后**登录成功** → 我们误以为验证通过。但那走的是**旧路**（富的专用 App），根本没验到新路。**整个门槛①白做。**

   **正确做法：直接把这个 URL 发给他，点开即走 FBIF App，不经过按钮选择：**
   ```
   https://shorturl.garyzheng.com/auth/feishu/fbif/login
   ```

   > 兜底：就算他点错了我也能识破——走对了 DB 里是 `fbif:<open_id>`，点错按钮是 `fude:<open_id>`。第 4 步的精确查询会暴露这一点。

3. **我（AI）**：SSH 生产查日志，抽出这次登录的 `open_id` 和 `tenant_key`：
   ```bash
   ssh aliyun-prod 'pm2 logs web-short-url --lines 200 --nostream | grep "login ok via fbif"'
   # 期望：[feishu] login ok via fbif tenant_key=<富的的> open_id=ou_xxx name=<富的同事>
   ```

4. **我（AI）**：用**完整本地主键精确定位**这一行（生产库已有同名重复记录，只按 name 查会认错行）：
   ```bash
   ssh aliyun-prod 'cd /opt/web-short-url && sqlite3 -header shorturl.db \
     "SELECT open_id, tenant, tenant_key, name FROM users WHERE open_id = '"'"'fbif:<上一步的open_id>'"'"';"'
   # 期望：tenant_key = 富的自己的 tenant_key（不是 FBIF 的）
   ```

**✅ 全过 → 新路已证明可用，开始改代码。**

**❌ 任何一步不过 → 停止迁移。但"停止"不等于"什么都不用做"：**

⚠️ **必须让用户去飞书后台把「应用共享」撤销掉**（Codex 提出）。
共享是**飞书后台的外部状态，`git revert` 撤不掉它**。如果代码停在双 App 版而共享还开着：
- 富的员工点 FBIF 按钮 → 能登进去 → 拿到 `fbif:<open_id>` 身份
- 富的员工点富的按钮 → 也能登 → 拿到 `fude:<另一个open_id>` 身份
- **同一个人裂成两个账号、两套历史** ← 这才是真正的烂摊子

同时清掉门槛①产生的金丝雀数据（见「回滚方案」的 SQL）。

**不需要做的**（已实测确认）：
- ❌ 不用加 redirect URL 白名单 —— `/auth/feishu/fbif/callback` **已经在白名单里了**
- ❌ 不用动富的的飞书后台 —— 单应用后富的侧零操作
- ❌ 不用改 `.env` —— 生产 `.env` 不动
- ❌ 不用管 `FEISHU_ALLOWED_TENANT_KEYS` —— **已 SSH 实测：生产未配置该变量**，白名单关闭，不会拦富的
  > 但如果将来要开白名单，**必须同时填 FBIF 和富的两个 tenant_key**——只填一个会把另一家全部 403 拦掉。

### 门槛 ②：部署后烟测（回归，确认新代码没把已证明可用的路搞坏）

门槛①已经证明"富的能通过 FBIF App 登录"。门槛②验的是**新代码有没有把它搞坏**。

> 🚨 **门槛①那次登录会种下 30 天 session，它会把门槛②变成假验证**（Codex 提出）。
> 富的同事直接开 `/login` → `checkAlreadyLoggedIn()` 检测到已登录 → **直接跳主页**——新按钮根本没点过、OAuth 根本没走。

**解法：不求用户配合，我直接把服务端 session 删掉**（比"请用无痕窗口"可靠——它由我控制）：

```bash
# 部署后、烟测前：吊销门槛①留下的 session，强制重新走一遍完整登录
ssh aliyun-prod 'cd /opt/web-short-url && sqlite3 shorturl.db \
  "DELETE FROM sessions WHERE open_id = '"'"'fbif:<富的open_id>'"'"';"'
```
删完他的浏览器即使还揣着旧 token，`/api/me` 也认不出来了 → 必然停在登录页 → 必然点新按钮。

**判据不是"能进主页"，而是「那个富的账号名下出现了一条新 session」**。

因为烟测前已经把他的 session **删光了**，所以——**只要他名下再出现任何一行，就是本次重新登录的铁证**（连时间戳都不用比）：

```bash
ssh aliyun-prod 'cd /opt/web-short-url && sqlite3 -header shorturl.db \
  "SELECT open_id, created_at FROM sessions WHERE open_id = '"'"'fbif:<富的open_id>'"'"' ORDER BY created_at DESC LIMIT 1;"'
# 有行 = 真的重新登录了；无行 = 他压根没走完登录
```

> ⚠️ **必须用精确的 `open_id =`，不能用 `LIKE 'fbif:%'`**（Codex 抓到的）——烟测里我自己（FBIF 账号）也要登一次，用 LIKE 会把**我的**新 session 混进结果，污染对富的的验证。
>
> ⚠️ **为什么不查 pm2 日志时间戳**：`pm2 logs` 默认**不打时间戳**，`ecosystem.config.cjs` 里也没配 `time` / `log_date_format`——那个判据根本跑不通。而 `sessions.created_at` 是 schema 里就有的真实时间字段。

**烟测清单：**

1. 富的账号走新 Mascot 单按钮 → 能进 → **精确查他名下的 session，出现新行即通过**（烟测前已删光，有行就是新登的——不用比时间戳）
2. FBIF 账号（我自己的）登一次 → 能进
3. `curl /auth/feishu/fude/login` → **404**（旧路由删干净了）
4. `curl /auth/feishu/fbif/qr-config` → **404**（扫码删干净了）
5. **端内 SSO 免登**（见下方单独说明）

### 端内 SSO 免登的烟测（**同样会被短路，而且更难清**）

`trySsoLogin()` 开头就有 `if (storedToken) return;`——它看的是**客户端 sessionStorage**，不是服务端 session。**所以我删服务端 session 对它没用**，飞书 webview 里只要还有 token，SSO 就直接跳过不跑。

必须满足下面**任一条**才算真验证：
- (a) 用一个**从没在这台设备/webview 上登过**的账号试，或
- (b) 在飞书客户端里清除该站点数据 / 清缓存后再打开

**判据**：日志里出现 `[feishu] sso login ok via fbif ...`（`handleSsoExchange` 打的，跟 OAuth 的 `login ok via` 不是同一行）。

⚠️ **但"存在这行"不够**（Codex 抓到的）——日志**没有时间戳**，历史里可能早就有部署前的记录。必须**比增量**：

```bash
# ① 烟测【前】先记基线条数
ssh aliyun-prod 'pm2 logs web-short-url --lines 500 --nostream | grep -c "sso login ok"'

# ② 用户在飞书客户端里打开（清过站点数据 / 换没登过的账号）

# ③ 烟测【后】再数一次 + 看最后一行是不是测试账号
ssh aliyun-prod 'pm2 logs web-short-url --lines 500 --nostream | grep "sso login ok" | tail -1'
```

**过的条件**：条数 **+1**，且最后一行的 `open_id` / `name` 就是这次的测试账号。

⚠️ 条数没涨、或涨了但不是测试账号 → **如实标"端内免登未验证"**。不许因为"页面进去了"就当它通过——那可能只是老 session 在起作用。

**不过 → revert（见下）。**

## 回滚方案（三件事，缺一不可）

**回滚不是"跑一条 git 命令"。** 这次改动同时动了三个地方的状态：**代码（git）+ DB（session）+ 飞书后台（应用共享）**。git 只能撤第一个。

### ① 代码

```bash
git revert <commit> && git push    # 自动部署会把旧版推回生产
```
生产 `.env` 没动过 → 旧代码回去后 fude 变量还在，**双 App 立刻恢复工作**。DB schema 没改，无需回滚。

### ② DB：清掉金丝雀 session（Codex 提出）

门槛①的富的同事登录会写入 1 行 `users` + 1 个 **30 天 session**。回滚后这个 session **仍然有效**。

```bash
# 先删 session（外键约束：必须先删 session 再删 user 行）
ssh aliyun-prod 'cd /opt/web-short-url && sqlite3 shorturl.db \
  "DELETE FROM sessions WHERE open_id = '"'"'fbif:<富的open_id>'"'"';"'

# 用户行：留着是孤儿数据（旧代码下富的走 fude App，会另建 fude:<open_id> 行），无害但脏。想删干净：
#   DELETE FROM users WHERE open_id = 'fbif:<富的open_id>';
```

### ③ 飞书后台：**撤销「应用共享」**（Codex 提出，最容易漏）

**这一步 git 撤不了，必须用户手工去后台点。**

不撤的后果：旧版（双 App）恢复后，富的员工**两个按钮都能登**——点 FBIF 得 `fbif:` 身份，点富的得 `fude:` 身份，**同一个人裂成两个账号、两套历史**。

> 如果**有意保留**共享（比如想留着以后再试），必须明确知道并接受这个身份分裂风险，且在 README 里写清楚。

---

**"回滚干净"的真相：代码零成本，DB 要手工清一行，飞书后台要手工撤一次。** 别把它说成零。
